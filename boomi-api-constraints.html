Boomi API Constraints for EDMS Ingestion and Retrieval

Size, timeout, concurrency and rate limits across Boomi CAM and the Boomi iPaaS runtime. Boomi and Doxis both hosted on AWS; API only, no MFT · v0.2 (draft) · 18 November 2026

How to use this page

  1. Section 2 lists each published limit with a link to the Boomi documentation it came from. Values were checked on 18 November 2026; Boomi changes these between releases, so recheck before baselining.
  2. Section 3 shows which limit affects each EDMS API and the proposed way round it.
  3. Section 3a lists API-only ways to handle large files. Sections 4 and 5 are the guardrails to agree and the questions to put to Boomi and the platform owner.
  4. Each table has a "Copy for Word" button.

1. Bottom line

Boomi is built for many small, quick API calls, not for moving large files through a synchronous API. On a Boomi-hosted runtime (public or dedicated cloud) an inbound API request is capped at 5 MB, Low Latency calls are cut off at 30 seconds, and each execution worker runs 20 calls at once. CAM adds a 60 second backend timeout unless Boomi extends it. On our own runtime (local Atom, Molecule or private runtime cloud) most of these limits are configurable and unlimited by default, so memory, disk and timeouts become our sizing problem.

For EDMS this means the JSON operations (search, representations, retention) fit comfortably, but create and retrieve need a size threshold and an API-only route for larger files (section 3a). Boomi and Doxis are both on AWS, so if they share a region the network leg is short and file size and Doxis response time dominate.

Request size (Boomi cloud)5 MB
Low Latency time limit30 s
CAM backend timeout60 s (more via support)
Worker concurrency20 running per worker
Request rate (public cloud)5 to 20 per second per node
Large filesRanged, chunked or direct-to-storage APIs (section 3a)

3a. API-only options for large files

OptionHow it worksFits the limits becauseDepends onUse for
A. Ranged downloadConsumer reads the file in byte ranges with the HTTP Range header (for example 4 MB per call). Boomi passes the range to Doxis and returns 206 Partial ContentEach call is small, finishes well inside 30 s and 60 s, and bounds memory per callDoxis supporting ranged or offset readsGet content stream
B. Chunked upload sessionPOST opens an upload session; the consumer PUTs numbered chunks under the size limit; a final call commits, checks the SHA-256 and creates the document in DoxisEvery request stays under 5 MB and 30 sDoxis supporting chunked or append upload, or Boomi staging the chunks (needs storage)Create document
C. Direct-to-storage linkThe API returns a short-lived signed URL and the consumer uploads to or downloads from storage directly (for example S3 in the Doxis AWS account). Boomi handles only the metadata callsThe file never passes through CAM or BoomiDoxis keeping content in S3 or issuing its own signed URLs; security approval for bearer linksCreate and get content, largest files
D. Asynchronous createPOST returns 202 Accepted with a status URL; Boomi writes to Doxis in General mode and the consumer pollsTakes the Doxis write out of the 30 s and 60 s limits; the upload itself must still fitSelf-run runtime, or General mode within 10 min on a Boomi-run workerCreate document when Doxis is slow
E. Raise the limitsRun the Boomi runtime ourselves on AWS, raise request size, worker time and heap, and ask Boomi to extend the CAM timeoutLimits become our own settingsSelf-run runtime (Q2); Boomi support for CAM over 60 s; heap sized for concurrency times file sizeModerate file sizes only; does not scale to very large files

A and B cover retrieve and create without new storage. C scales best but needs Doxis to expose its storage or signed URLs. Suggested start: agree the threshold (G1), use A for retrieval, and choose B or C for create once Q6 is answered.
