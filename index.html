  1.   3. Read the journey summaries, then the consolidated diagram. Box colour shows the system doing the work; line style shows the integration type. Step numbers in each box match the source sequence diagrams.
  4. Use the requirement filters to narrow by category or search by text, for example NRS, eDMS, file collection or a step reference such as J3 steps 18. Each requirement cites the source steps it came from.

  7. Read the interaction diagram top to bottom: black bars separate the journeys, numbered arrows follow the source step numbers, and red notes point to open items. Use Actual size and scroll, or Fit to width for an overview.

Journeys

Three journeys. NRS submission and eDMS ingestion run as parallel legs inside Journey 3; Journey 1 step 45 reuses the eDMS leg for thread attachments.

  • J1

    Create Thread

    Actor: Internal user (thread owner)

    Trigger: Internal user selects Create Thread in the workspace (already authenticated and authorised to create threads)

    Outcome: Thread in pending status with technical and business reference; attachments passed to eDMS; recipient notified (proposed)

    HIP involvement: File upload per attachment (separate File Upload sequence, pattern TBC); eDMS transfer at step 45; thread confirmation event (proposed)

    Recipient (external user) is asked to provide documents: leads into J2

  • J2

    External User Document Upload

    Actor: External user

    Trigger: External user selects documents to upload against a thread interaction

    Outcome: Documents clean-staged in HIP (or quarantined); session, interaction and document state updated; user notified

    HIP involvement: File Transfer API, pre-signed URL generation, landing bucket, AV scan, quarantine, clean staging, upload outcome events

    Clean-staged documents are referenced by the submission: leads into J3

  • J3

    External User Submission (crystallisation)

    Actor: External user; Internal user notified

    Trigger: External user clicks submit on the interaction response

    Outcome: Signed submission with attachments held by NRS (evidential) and ingested by eDMS; both users notified; staged files deleted

    HIP involvement: NRS Submission and Attachment APIs via API Management; file transfer request queue; transfers to NRS and eDMS; transfer, acceptance and deletion events

    End of journey

Principles

PrincipleHow it applies
HIP mediates every cross-platform integrationCalls and events that cross MDTP, HCP, HIP, NRS or eDMS boundaries pass through HIP API Management or Event Management, giving one security, throttling and observability model (OI-19, OI-20).
Thread Manager orchestrates; HIP executesThread Manager owns journey state and decides what happens next. File Transfer Manager moves files on command and reports outcomes; it holds no journey logic.
File content never passes through front ends or Thread ManagerBrowsers upload directly to HIP storage with pre-signed URLs; onward transfers read from clean staging.
Asynchronous by default for long-running workUpload scanning, NRS and eDMS transfers and deletion are asynchronous commands and events. Synchronous calls are short and return acknowledgements.
Configuration over constructionFile Transfer Manager runs one generic transfer engine. NRS and eDMS are configuration rows (target type, endpoint, credentials, retry policy), not separate processes.
Contract firstEvery API has an OpenAPI contract and every event or command an AsyncAPI contract before build. Contracts are versioned and owned.
Idempotent and traceableEvery request and message carries an idempotency key and a correlation id; consumers tolerate duplicates.
Independent legsNRS and eDMS legs run in parallel and do not depend on each other; clean-up waits for both.

APIs

API-01 Create thread Integration (MDTP to HCP)

POST /threads (proposed; source: POST Thread Service API)
Consumer: Front-end Service (internal) | Provider: Thread Manager (Thread Service) | Mediation: HIP API Management (recommended, OI-19)

Create the thread record once the internal user has entered the recipient's contact details, so a thread reference exists before files are attached.

Requirements: INT-01, NFR-01, NFR-04 | Open items: OI-01, OI-02, OI-06, OI-19

API-02 Save thread details (front end) Front end (context only)

PUT Thread Service API (front end)
Consumer: Internal user browser | Provider: Front-end Service (internal) | Mediation: None

Save message title, body and attachment list while the internal user builds the thread; details are cached in the front end until submission.

Requirements: NFR-06 | Open items: OI-24

API-03 Change thread details (front end) Front end (context only)

PUT Interaction API (front end)
Consumer: Internal user browser | Provider: Front-end Service (internal) | Mediation: None

Save changes made from the Check Answers loop. The source design names this the Interaction API, while step 21 uses Thread Service API for the same action; one name should be agreed.

Requirements: context only | Open items: OI-24

API-04 Submit thread Integration (MDTP to HCP)

PUT /threads/{threadId}/submission (proposed; source: PUT Submission Service API)
Consumer: Front-end Service (internal) | Provider: Thread Manager (Submission Service) | Mediation: HIP API Management (recommended, OI-19)

Confirm the thread, return the business reference for the confirmation page, and start the transfer of thread attachments to eDMS.

Requirements: INT-02, INT-03, EVT-07, EVT-12 | Open items: OI-05, OI-08, OI-09, OI-19

API-05 Request document upload (front end) Front end (context only)

POST /document_uploads (source)
Consumer: External user browser | Provider: Front-end Service (external) | Mediation: None (front end calls API-06 through HIP)

Start an upload for the files the external user selected and return pre-signed URLs to the browser.

Requirements: INT-04, EVT-01 | Open items: OI-20

API-06 File Transfer API: request upload Integration (MDTP to HIP)

POST /file_uploads (source)
Consumer: Front-end Service (external and internal) | Provider: HIP File Transfer Manager | Mediation: HIP API Management

Validate the files to be uploaded, choose single or multi-part upload, issue pre-signed URLs and create the file collection.

Requirements: MFT-01, MFT-02, MFT-13, INT-04 | Open items: OI-21, OI-22, OI-26

Consumer: User browser | Provider: HIP landing bucket (S3) | Mediation: Pre-signed URL (no gateway)

Move file content from the browser to HIP storage without passing through SDEC services, and tell File Transfer Manager the upload is complete.
