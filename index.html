Boomi MFT — Proof-of-Concept Connectivity & File-Transfer Question Set

Discovery & readiness checklist to run before building the two connectivity proofs of concept on Boomi native MFT.

v1.028 July 2026Integration ArchitectureBoomi native MFT (Thru)OFFICIAL — Programme Working Document

How to use this page

  • This page is the discovery checklist to run before building either proof of concept. It mirrors the downloadable Word document exactly — use the sticky download bar at the very top to pull the Word version (the artefact to circulate for the kick-off) or the full zip bundle.
  • Items marked Q are questions to put to the platform, network or security owner. Items in the red / amber boxes are open decisions that need a named owner before build — raised proactively, not deferred. They are collected in the decisions register.
  • Two flows are in scope and are assessed independently. The two pages to take into the kick-off are the decisions register (§10) and the per-endpoint grid (§11).
  • The single biggest determinant of the second POC’s feasibility and timeline is runtime placement plus the inbound firewall change — start those conversations first.

The two proof-of-concept flows

POC-1 · SaaS → SaaS Quadient (SaaS)──▶ Boomi native MFT──▶ Toxus (SaaS) Most likely public-internet path; the lower-risk of the two.
POC-2 · SaaS → internal Cloud SaaS source──▶ Boomi native MFT──▶ Internal landing zone Crosses the trust boundary into the internal network — materially harder; drives the critical-path decisions below.

Endpoints to interrogate: Quadient, Toxus, the cloud SaaS source, and the internal landing zone.

1 · POC scope & success criteria

Pin these down first — an undefined pass condition is the most common reason a POC “succeeds” but proves nothing usable.

  • What single sentence defines “POC passed” for each flow? (e.g. a synthetic file transfers end-to-end, integrity verified by checksum, and an audit record is produced.)
  • Is the goal connectivity only, or must the POC also demonstrate pattern fit (config-over-construction), the security controls, and operational fit (logging, alerting, audit)?
  • Are the two flows assessed separately, or must the second chain from the first? Confirm they are decoupled.
  • Which environment does each endpoint expose — non-production or production only? Confirm both POCs run in non-prod.
  • What is the time-box and hard exit date, and who owns the overall POC?
  • What evidence pack do stakeholders need to declare a pass (logs, checksums, audit record, screenshots)? Agree the format up front — the evidence is itself a deliverable.

2 · Endpoints & protocols (ask per endpoint)

Repeat for each of the four endpoints.

  • What transfer protocol does the endpoint support — SFTP, FTPS, AS2, HTTPS/REST, S3/blob, or a Boomi native MFT client?
  • Does it act as a server (we connect to it) or a client (it connects to us)? i.e. who initiates the connection?
  • Is the model push or pull — do we poll a directory, receive a webhook, or get pushed to?
  • Is the host/port/URL a stable static value, or dynamically provisioned?
  • Is there a Boomi-native / MFT connector, or do we use the generic SFTP / HTTP connector?

Platform-specific

  • Quadient — which product and edition (Inspire / Impress / Cloud)? What does it expose for outbound — an SFTP drop, an output-management dispatch, or an API? Does it push, or must we pull?
  • Toxus — what is the documented ingress mechanism, and are there payload/format constraints on inbound files?
  • Cloud SaaS source — confirm the platform, its egress mechanism, and whether it can target a private endpoint or only a public one.
  • Internal landing zone — is it an SFTP server, a file share, an object store (S3/blob), or a directory? Who technically owns it?

3 · Connectivity & network path

POC-1 — SaaS → SaaS (Quadient → Toxus)

  • Does traffic traverse the public internet, or is a private interconnect available/required?
  • Does either platform enforce IP allow-listing? If so, we must supply our egress IPs and obtain theirs.
  • What are the static egress IPs of the Boomi runtime (Atom Cloud region vs local Atom), and are they guaranteed stable?
  • Any data-residency constraint that fixes the runtime region (e.g. UK)?

POC-2 — Cloud SaaS → internal landing zone (the hard path)

★ Decision — runtime placement is the critical dependency

To reach an internal landing zone you almost certainly need a local Atom/Molecule inside the network zone, OR a private circuit (VPN / ExpressRoute / Direct Connect / PrivateLink) from the Atom Cloud. Which one is decided here — and it drives feasibility, cost and timeline more than anything else in this document. Owner: Network / Platform Engineering — resolve before any build.

  • Where does the Boomi runtime execute — local Atom in-zone, or Atom Cloud over a private circuit?
  • Which trust zone is the landing zone in, and what perimeter controls sit in front (firewall, reverse proxy, WAF, ICAP/AV)?
  • The flow is inbound to the zone — does the direction of connection initiation align with firewall policy? Inbound into the estate is typically restricted, so the internal side may need to pull, or a DMZ broker may be required.
  • Is there an existing DMZ / landing-zone edge (e.g. an SFTP perimeter) we should target instead of the internal host directly?
  • Firewall change: source IPs, destination host/port and protocol — who owns the rule, and what is the lead time? (Usually the critical-path item — start it now.)
  • DNS — can the runtime resolve the landing-zone host? Is split-horizon DNS in play?
  • Is there an egress proxy in the zone, and does it require authentication?

4 · Authentication & credentials (ask per endpoint)

  • What auth method — SSH key pair (SFTP), mTLS / client certificate, OAuth2 client-credentials, API key, AS2 certificates, or username/password?
  • Whose keys/certs, and what is the exchange process and lead time (public-key swap, CA-signed vs self-signed, expiry dates)?
  • For SFTP — do we have the server host-key fingerprint to pin, to prevent a man-in-the-middle?
  • Where are secrets stored for the POC — Boomi secure vault, or CyberArk PAM? PAM is a flagged platform gap (G-14); confirm it is available, or agree a documented interim secret store with an exception.
  • Who owns each credential, and what is the rotation/revocation plan (including revocation at teardown)?

5 · Security, data classification & compliance

★ Decision — synthetic data only, especially into the internal zone

For a connectivity POC there is no reason to move real data. Insist on synthetic / anonymised files with no PII or taxpayer data — most critically for the flow into the internal zone. Get this stated and owned before a single file moves. Owner: Data Protection / Information Assurance.

  • What data is in the sample file? Confirm it is synthetic / anonymised.
  • What is the data classification (OFFICIAL / OFFICIAL-SENSITIVE), and is that classification permitted to traverse SaaS-to-SaaS over the public internet?
  • Encryption in transit — what TLS version floor and cipher policy is mandated at each hop?
  • Is file-level encryption (PGP/GPG) required on top of transport, and who holds the keys?
  • Encryption at rest — required at each hop and in the landing zone?
  • AV/malware scanning on ingress to the internal zone — via Windows MDE (~250 MB scan limit, flagged gap G-15) or an ICAP service? Is the sample file within the scan limit?
  • Are DLP controls enforced on the landing zone that could quarantine the file?
  • Is a DPIA, security assessment or formal risk acceptance required before any file (even synthetic) crosses into the internal zone, and who signs it?

6 · File handling & integrity

  • What is the file format, size, encoding and naming convention?
  • How is completeness detected so a partial file is never processed — trailing sentinel (.done), rename-on-complete, or size-stable polling?
  • How is integrity verified — is a checksum/hash (SHA-256) captured at source and re-verified at target? Is a manifest provided?
  • How are duplicates and re-sends handled (idempotency)?
  • Is any character-set or line-ending transformation needed between the platforms?
  • For the POC — a single file, or a small batch to also prove polling/looping?

7 · Boomi runtime & MFT capability

★ Decision — is the POC disposable, or must it demonstrate config-over-construction?

If each transfer is hand-built as a bespoke process, the POC proves connectivity but nothing about the target design. Agree up front whether the POC must map each transfer to a configuration row on the single generic MFT engine — otherwise it validates the wrong thing. Owner: Integration Architecture.

  • Which Boomi runtime and version, and is native MFT (Thru-powered) the capability under test, or generic SFTP/HTTP connectors? Be explicit — test the thing you will actually build on.
  • Is native MFT licensed/entitled in the POC environment?
  • Does each transfer map to a config row on the generic engine, or is it a throwaway build?
  • Where is the Atom placed (cloud vs local), and does that match the network path in §3?

8 · Observability, error handling & operations

  • Where do success/failure events surface — is Dynatrace wired in for the POC, per the estate standard?
  • Is failure alerting configured for the POC?
  • What is the retry/resubmission behaviour on transient failure?
  • Is a governance-grade audit trail produced (who/what/when for each transfer)? This is a required evidence artefact.

9 · Governance, approvals & exit

  • Is change approval (CAB) required for the firewall/network change into the internal zone, and what is the lead time?
  • Who are the named approvers — security, network, data protection, and each platform owner?
  • Who signs off the POC as passed, against the criteria agreed in §1?
  • What is the teardown plan — revoke credentials, remove firewall rules, delete synthetic data — and who owns it?
