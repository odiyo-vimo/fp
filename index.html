1. Objective

The objective of this MVP is to prove, on live infrastructure and with a real production feed, that Boomi MFT can carry a scheduled file transfer end to end across both of the trust boundaries the platform will be asked to serve, and to do so as a configuration change rather than as a new build. Everything in this document exists to test that single proposition.

The MVP is deliberately narrow. It is not a pilot of the target operating model, not a migration of the incumbent estate, and not a self-service portal release. It is the smallest piece of work that produces a defensible answer to five questions:

  1. Can Boomi MFT move a file internal to internal, from a source system landing area into a data warehouse preparation zone, without a bespoke Boomi component per interface?
  2. Can the same platform, using the same generic engine and a second configuration row, move a file internal to external to an other government department endpoint?
  3. Does the platform satisfy the security, credential and scanning controls that apply to an OFFICIAL feed containing personal data, without exception or waiver?
  4. Is the operational evidence, audit trail, alerting and reconciliation good enough that Service Operations will accept the flow into support?
  5. What does the effort curve actually look like, so that the onboarding estimate used in the wider business case is grounded in measured effort rather than assumption?
Success is a decision, not a demo. The MVP concludes with a go, go-with-conditions, or no-go recommendation supported by an evidence pack that a Design Authority can audit.

2. MVP candidate

The selected candidate is feed ADR.040, the quarterly Migrant Workers Scan extract, which flows from NPS into the ADR data preparation zone and onward to the Office for National Statistics. The candidate is unusual and valuable because a single business feed contains both of the transfer patterns the platform must prove, using one dataset, one owner community and one test cycle.

2.3 Why this candidate was selected

  • It is genuinely dual-pattern. One onboarding exercise yields evidence for both the internal and the cross-boundary case, which halves the calendar cost of proving the platform.
  • The volume is trivially small. One file per quarter means the MVP tests correctness, control and operability rather than throughput, which is the right thing to test first.
  • The current leg B path traverses an Insecure IF server. Retiring that hop is a security improvement that gives the MVP a business benefit independent of the platform decision, which strengthens the case for funding the run.
  • Both endpoints are already known and already in production, so the MVP is not gated on a new system going live.
  • The quarterly cadence means a failed cutover has a long, forgiving recovery window rather than a same-day incident.

2.4 The candidate's principal weakness, stated plainly

A quarterly feed produces four natural test opportunities a year. Waiting for organic runs would stretch the MVP across two quarters and make the evidence base thin. The MVP therefore uses controlled replay of representative files as its primary proving mechanism, and reserves the natural cycle for a single parallel run. This is called out here so that no reviewer mistakes replay evidence for production-cycle evidence.

Natural cycle dateUse in the MVP
1 October 2026Too early. Firewall change lead time and endpoint agreement with ONS will not have completed. Observe the incumbent run and capture baseline timings and file characteristics only.
1 January 2027Parallel run. Boomi MFT executes both legs alongside the incumbent path. Outputs reconciled byte for byte. No production dependency on the Boomi path.
1 April 2027Target first production cycle on Boomi MFT for both legs, subject to the go decision at the end of the parallel run.

3. Scope

3.1 In scope

  • Two MFT flows, one per leg, delivered as configuration rows consumed by the generic engine process. No bespoke Boomi component may be created for either leg.
  • Runtime placement and connectivity for an internal source endpoint and an external destination endpoint.
  • Scheduling equivalent to the current quarterly trigger, including the check for file, wait and retry behaviour currently performed by Maestro job 1.
  • Credential sourcing for both legs, including the attempt to source from the enterprise secrets store and the documented outcome if that is not possible.
  • Anti-virus scanning of the file in transit and the behaviour when a scan fails or the file exceeds the scan ceiling.
  • Error handling, quarantine, archive and retention behaviour.
  • Audit trail, transfer logging, alerting and the operational handover pack.
  • A measured effort record for every onboarding activity, used to calibrate the wider onboarding estimate.

3.2 Out of scope

  • Any change to the Maestro job chain that stages and extracts the data inside ADR. Boomi MFT delivers into and collects from the existing file areas; the internal processing is untouched.
  • Any change to the content, schema or business meaning of the file.
  • Self-service request, approval or provisioning through the portal. The MVP is configured by the platform team.
  • CI/CD promotion of configuration rows between environments. This is a known platform gap and is handled manually and evidenced, not solved (G-13).
  • Decommissioning of UTM, the IF server or SDES. The MVP proves the alternative; decommissioning is a separate decision with separate stakeholders.
  • Any other feed in the ADR warehouse or any other warehouse.
  • Throughput, large file and high frequency testing.

3.3 Explicit non-goals

The MVP does not attempt to demonstrate that Boomi MFT is cheaper than the incumbent, does not attempt to establish the target operating model, and does not attempt to prove the platform at scale. Claims of that kind made on the back of this MVP would not be supportable by its evidence.

4. Current state

The as-is path is a chain of scheduled Maestro jobs operating over shared file areas inside ADR, bracketed by a UTM transfer on the way in and an Insecure IF server and SDES on the way out.

  1. The upstream supplier produces a flat file from the migrant data store.
  2. UTM transfers the flat file into the NPS file landing area inside ADR.
  3. Maestro job 1 becomes active on the first day of each quarter and polls the landing area for the expected file. If the file has not arrived the job re-checks on its schedule.
  4. On arrival, Maestro job 2 moves the file out of the landing area.
  5. Maestro job 3 stages the data into the MWS database staging area.
  6. Maestro job 4 extracts the staged data back out into files in the MWS file output area.
  7. Maestro job 5 transfers the output files to the target server, traversing an Insecure IF server and then SDES to reach ONS.

5. Target state

In the target state Boomi MFT owns the two boundary movements and nothing else. The internal Maestro staging and extraction chain is retained as is. Leg A collects the supplier flat file and delivers it into the NPS file landing area, at which point the existing chain proceeds unchanged. Leg B collects from the MWS file output area and delivers directly to the ONS endpoint, removing the IF server hop.

16. Rollback and fallback

  1. The incumbent UTM and IF and SDES paths remain configured and operable throughout the MVP, including during and after the parallel run.
  2. During the parallel run the incumbent path is authoritative. The Boomi path is observed only, and its output is reconciled but not consumed downstream.
  3. At production cutover the rollback trigger is any of: failure to deliver within the agreed arrival window, reconciliation mismatch, ONS rejection, or a security control failure.
  4. Rollback is the re-enablement of the incumbent job schedule and the disabling of the two configuration rows. It is proven and timed at S-15 before cutover is approved.
  5. Because the feed is quarterly, a rollback at cutover costs one cycle at most and can be executed inside the normal arrival window without business impact, provided it is detected promptly. This is why SC-06, detection of non-arrival, is a hard criterion.

17. What the MVP tells us about the wider programme

The value of the MVP is not the two flows. It is the calibration it gives to every subsequent onboarding conversation.

Question the programme will be askedWhat the MVP provides
How long does it take to onboard a file transfer?A measured split between configuration effort, which is expected to be small, and dependency lead time, which is expected to dominate. SC-13.
Do we need a developer per interface?A direct answer, evidenced by the engine gap log. SC-12.
Can this platform cross a departmental boundary safely?Leg B evidence, including firewall, allow-list, transport security and acknowledgement. SC-02, SC-11.
What breaks first at volume?Nothing. The MVP does not answer this and must not be quoted as if it does. A separate throughput exercise is required.
What are the real platform constraints?Written impact statements against G-13, G-14 and G-15 with named owners. SC-17.
