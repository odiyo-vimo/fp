Overview

Three REST operations on Boomi API Management: API 1 issues presigned upload URLs, API 2 is the presigned URL itself (the consumer PUTs the file and must pass the document ID), API 3 deletes a file by the consumer's external document ID.

Files are held temporarily on the Boomi MFT SFTP server. Boomi writes each upload into /inbound, the MFT flow scans it and moves clean files to /available, and the file is removed by API 3 or when the 72-hour hold ends.

Boomi MFT cannot issue a presigned upload URL (its Content API presigns downloads only) and an SFTP server cannot accept an HTTP PUT, so Boomi issues and verifies the URL itself with an HMAC signature. This differs from IDD-FT-001, where the URL pointed at an S3 landing bucket.

API 1: Generate presigned URL

POST/file-transfer/v1/generate_presignedurl

Authentication: OAuth2 client credentials, scope file-transfer.upload.request

1.1 Description

The consumer asks for permission to upload one or more documents to the Boomi MFT platform. For each document it sends its externalDocumentId, documentName, fileSizeBytes, mimeType and SHA-256 checksum, with one correlationId for the call.

Boomi API Management authenticates the caller and validates the request. The generic Boomi process P01 applies the policy row for the sourceSystem, refuses an externalDocumentId that already has a live file, and for each accepted document creates a fileId and a presigned URL.

The URL is issued by Boomi, not by MFT: Boomi MFT has no presigned upload URL and its SFTP server cannot take an HTTP PUT. The URL is an HMAC-SHA256 signature over the upload path, the externalDocumentId, the size, the checksum and a 15-minute expiry. It works once, and only with the matching document ID header (API 2). The file will be held temporarily on the MFT SFTP server.

API 2: Upload to the presigned URL

PUT/file-transfer/v1/uploads/{fileId}?expires&kid&sig

Authentication: None: the signed URL is the credential (single use, 900 s)

2.1 Description

The consumer sends the file bytes with an HTTP PUT to the URL from API 1. The document ID must be passed: the X-External-Document-ID header is mandatory and must equal the externalDocumentId the URL was issued for. Because the ID is part of the signed string, a URL used with any other document ID fails.

Boomi process P02 reads the file row, checks the header, verifies the HMAC signature and expiry, and claims the URL with a conditional update so it can only be used once. It checks the SHA-256 of the received bytes against the signed checksum and the Content-Digest header, then writes the file to the MFT SFTP server under /inbound/{sourceSystem}/{fileId}.bin with the SFTP connector, followed by a zero-byte trigger file.

The trigger starts the MFT flow: anti virus scan, then a move to /available/{sourceSystem}/ where the file is held temporarily (72 hours by default). Boomi reads the outcome from MFT and publishes events (SD-3). If the checksum fails or MFT cannot be written, the URL is released for a retry until it expires.

API 3: Delete a file

POST/file-transfer/v1/delete_file

Authentication: OAuth2 client credentials, scope file-transfer.file.delete

3.1 Description

The consumer asks Boomi to delete a document from the Boomi MFT platform using its own externalDocumentId. The request also carries documentName, fileSizeBytes, a correlationId and an optional reason; name and size must match the record so a wrong ID cannot delete the wrong file.

Boomi process P04 takes the sourceSystem from the caller's client registration, finds the file by sourceSystem and externalDocumentId (assumption B-13), and acts on its state. A held clean file is removed from the MFT SFTP server with the SFTP connector Delete operation. An unused URL is revoked. A file still uploading or being scanned is marked DELETE_PENDING and removed as soon as MFT finishes.

The call is idempotent: repeating it returns ALREADY_REMOVED. Every completed delete publishes file_deleted on Boomi Event Streams.

3.3 Assumptions in Boomi

Can the external document ID be used to delete? Yes (B-13). It is unique among live files for a sourceSystem, the sourceSystem comes from the caller's client registration, so it resolves to exactly one file; documentName and fileSizeBytes must match before anything is deleted.

Boomi issues and checks the URL itself. The signature is base64url HMAC-SHA256, without padding, over this canonical string (lines joined with a line feed):

The URL carries expires, kid and sig. Because externalDocumentId, size and checksum are signed but not in the URL, the upload must send the matching X-External-Document-ID header and the matching bytes. The Groovy core was run against the Python reference and produces identical signatures.

DELETE_PENDINGP04Delete requested while UPLOADING or UPLOADED; P02 or P03 completes it.
DELETEDP04, P05, P03File removed from MFT (requested or hold period ended). Terminal.
EXPIREDP05URL not used before expiry. Terminal.
REJECTEDP01Failed policy at generate time; no URL. Terminal.

Non-functional and security design

AreaDesign
SecurityOAuth2 client credentials for generate and delete (scopes file-transfer.upload.request, file-transfer.file.delete); sourceSystem bound to client id; upload URL single use, 900 s, bound to document ID, size and SHA-256; TLS 1.2+; MFT service user with key auth.
IntegrityP02 computes SHA-256 of the received body and compares it with the signed checksum and Content-Digest before writing to MFT.
PerformanceGenerate p95 under 500 ms for 10 documents. Upload throughput bounded by gateway and Molecule; measure in POC (B-07).
AvailabilityNo partial state: a failed MFT write resets the file to URL_ISSUED so the same URL can be retried until expiry.
ObservabilitycorrelationId, fileId and externalDocumentId on every execution and event; URLs, signatures and documentName never logged.
IdempotencyIdempotency-Key on generate and delete; upload is single use; repeat delete returns the same outcome.
