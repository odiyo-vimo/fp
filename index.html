Presigned URLs: how they work and how to test one

A presigned URL lets someone with no account read or write one specific object for a few minutes. This page explains the signature, gives sample URLs, and has a test lab that signs and checks URLs in your browser.

How to use this page

  1. Read How it works for the two-minute version, then tap each coloured part of the URL in Anatomy to see what it does.
  2. Pick a URL from Sample URLs and press Load into test lab. The lab recomputes the signature and tells you whether the URL is valid, expired or tampered with.
  3. In the Test lab, use Demo signer to create a fresh URL that expires in 30 seconds. Verify it, then try the tamper buttons, then wait for it to expire and verify again.
  4. To test against a real bucket, use the Your own bucket tab (or the downloadable presign.py) with short-lived test credentials, then run the generated curl command from a terminal.
  5. For the Boomi build, download the Groovy script from the bar at the top and follow the steps in Boomi pattern. The sequence diagram is in the same bar as a draw.io file.

All signing and checking runs locally in your browser with Web Crypto. Nothing you type on this page is sent anywhere. Even so, only ever paste temporary, least-privilege test credentials.

How it works

A presigned URL is an ordinary object URL with an authorisation signature carried in the query string instead of a request header. Whoever holds a valid signing credential (here, a Boomi process) builds the URL; whoever holds the URL can perform exactly the operation it was signed for, on exactly that object, until it expires. The storage service never sees the secret key. It recomputes the signature from the request it receives and compares.

Signing (Boomi side)

  1. Write a canonical request: method, object path, sorted query parameters (algorithm, credential scope, timestamp, expiry, signed headers), the host header and UNSIGNED-PAYLOAD.
  2. Hash it with SHA-256 and wrap it in a string-to-sign with the timestamp and scope (date, region, service).
  3. Derive a signing key by chaining HMAC-SHA256 over date, region, s3 and aws4_request, starting from the secret key.
  4. HMAC the string-to-sign with that key and append the hex result as X-Amz-Signature.

Checking (storage side)

  1. Read the access key ID from the credential parameter and look up the matching secret.
  2. Rebuild the canonical request from what actually arrived: method, path, query, host.
  3. Recompute the signature. Any change to the method, object key, expiry or host gives a different value and the request is refused.
  4. Check the clock: refuse if now is later than X-Amz-Date plus X-Amz-Expires, then apply the signer's own permissions (IAM, bucket policy, KMS).

Two consequences matter for design. First, the URL is a bearer token: anyone holding it can use it, as many times as they like, until it expires. Second, it cannot be revoked on its own; you shorten its life, or revoke the credential that signed it.

Boomi pattern: external upload with a presigned PUT

Boomi stays in control of who may upload what, but the file bytes travel straight from the user's browser to object storage. Boomi never proxies the payload, so large files do not pass through the Atom, and the scan and filing steps start from a storage event.

Solid blue: request. Dashed grey: response. Green dashed: asynchronous event. Amber box: the signing step inside Boomi.

Building it in a Boomi process

  1. Listener. Web Services Server (or API Service component) operation POST /uploads, behind the gateway. Validate case reference, declared size and content type against the allow-list.
  2. Set Properties. Populate DPP_S3_BUCKET, DPP_S3_REGION, DPP_S3_METHOD=PUT, DPP_S3_EXPIRES=300 and a server-generated DPP_S3_KEY such as inbound/{caseRef}/{uuid}. Never take the key from the user.
  3. Credentials. Set DPP_S3_AK, DPP_S3_SK and, for temporary credentials, DPP_S3_TOKEN from encrypted environment extensions or the secrets store. This is the same open question as gap G-14.
  4. Data Process, Custom Scripting. Paste boomi_presign_url.groovy. It writes DPP_PRESIGNED_URL and passes documents through unchanged. It uses only JDK classes, so no custom library is needed.
  5. Message shape. Return {"uploadId": ..., "uploadUrl": "{DPP_PRESIGNED_URL}", "expiresAt": ...} with HTTP 201. Record the uploadId and object key for correlation.
  6. Second process. Triggered by the ObjectCreated event (queue listener). Check size and type of the stored object, run the AV scan, file to the document store, then update upload status.

Test the Groovy script outside Boomi

The signing functions in the script were checked against the Python signer and against AWS's own SDK (botocore) for GET and PUT, including an object key containing a space. Run python3 presign.py --selftest to reproduce the AWS documentation example, or generate a real URL:

export AWS_ACCESS_KEY_ID=... AWS_SECRET_ACCESS_KEY=... AWS_SESSION_TOKEN=...
python3 presign.py --bucket my-test-bucket --key test/hello.txt --method PUT --expires 300
curl -X PUT --upload-file ./hello.txt "PASTE_URL_HERE"      # upload
python3 presign.py --bucket my-test-bucket --key test/hello.txt --method GET --expires 300
curl -o hello-copy.txt "PASTE_URL_HERE"                      # download
# or, with the AWS CLI (GET only):
aws s3 presign s3://my-test-bucket/test/hello.txt --expires-in 300 --region eu-west-2

Design notes

Expiry is the main control
Keep upload URLs short (300 to 900 seconds). SigV4 allows up to 7 days, but a URL also stops working when the signing session's temporary credentials expire, whichever comes first. A bucket policy condition on s3:signatureAge can cap the age centrally regardless of what a caller asks for.
Reusable until expiry
A presigned URL is not single-use. Generate a unique, server-chosen key per upload so a replayed URL can only overwrite its own slot, and enable bucket versioning if overwrite must be detectable.
A presigned PUT cannot enforce size
The declared size is not signed in this pattern. Where the scan limit matters (G-15, about 250 MB), either use a presigned POST with a content-length-range policy condition, or reject oversized objects in the event-driven step before scanning.
Signed headers must match exactly
This script signs only host, so callers may send any Content-Type. If you add content-type to the signed headers to pin the type, the uploader must send exactly that value or receive SignatureDoesNotMatch.
Treat URLs as secrets
Do not log full URLs in Boomi process logs, gateway access logs or browser analytics. Log the object key and uploadId instead.
Browser uploads need CORS
A direct PUT from a web page needs a CORS rule on the bucket that allows the portal origin and the PUT method.
Encryption keys
If the bucket uses SSE-KMS, the signing identity also needs the matching KMS permissions, otherwise the URL signs correctly but the request is refused.
Presigned URL versus share link
A presigned URL is self-validating: storage checks the maths, not a database. A share link from a file-sharing service is usually an opaque token looked up server-side, which can be revoked individually. Keep the two distinct in requirements wording.
