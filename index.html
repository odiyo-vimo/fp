2. Authentication: OAuth 2.0 Client Credentials

All SDEC integration patterns use OAuth 2.0 client credentials: SDEC exchanges its client ID and secret for a short-lived bearer token, then presents that token on every API call. The integration supports app-to-app authentication only.

Key points

TopicGuidance
Grant typeClient credentials (RFC 6749, section 4.4). Machine to machine, no user involved, no refresh token. When the token expires, SDEC requests a new one.
Who callsOnly SDEC server-side components hold the client secret and call the token endpoint and the APIs. The browser only ever receives a presigned URL.
Client registrationOne client per consuming system per environment (dev, test, pre-prod, prod). Each client_id maps to one sourceSystem value and a fixed set of scopes.
Token requestPOST to the token endpoint with form-encoded grant_type=client_credentials and the scopes needed. The client authenticates with HTTP Basic (client_id:client_secret) over TLS.
Token responseaccess_token (signed JWT), token_type Bearer, expires_in (proposed 3600 seconds, D-13) and the granted scope.
Using the tokenSend Authorization: Bearer <access_token> on every API call. Never put the token in a query string, URL or log line.
CachingReuse the token until shortly before expiry (for example renew when less than 60 seconds remain). Do not request a token per API call; the token endpoint is rate limited.
Validation at the GatewaySignature checked against the issuer's JWKS (cached), then iss, aud, exp and nbf (small clock-skew allowance), scope against the operation, and client_id against sourceSystem.
ErrorsToken endpoint: 400 invalid_request or invalid_scope, 401 invalid_client. API: 401 invalid_token means discard the cached token, fetch a new one once and retry; 403 insufficient_scope is a configuration fault and must not be retried.
Secret rotationTwo secrets are valid during a rotation window so SDEC can switch without downtime. Rotation period agreed with security (D-13).
Hardening optionprivate_key_jwt (RFC 7523) or mutual TLS client authentication (RFC 8705) removes the shared secret. Recommended for decision before go-live (D-15).

Token flow

Steps 1 to 4 run once per token lifetime, not per call. Steps 5 to 9 repeat for every API call while the cached token is valid. For NRS calls, HIP replaces the SDEC token with HIP-managed NRS credentials on the onward leg (S-14).

Host: <authorisation-server>
Authorization: Basic base64(client_id:client_secret)

3. Integration Patterns (section 5.2)

Pattern table

PatternDescription
Synchronous APIRequest and response over HTTPS (REST, JSON) through Boomi API Gateway; SDEC receives the result in the same call. Used for: generate presigned URL (SDEC-MFT-API-01), get document status (SDEC-MFT-API-02), delete file (SDEC-MFT-API-03), NRS submission (SDEC-NRS-API-01) and NRS attachment URL (SDEC-NRS-API-02). Controls: OAuth 2.0 bearer token, Idempotency-Key on create and delete, X-Correlation-ID, agreed timeouts, Problem error structure. No file content passes through this pattern.
Asynchronous File UploadSDEC obtains a time-bound presigned URL through the synchronous API, then the browser uploads the file directly to Boomi MFT transient storage with HTTP PUT. Files up to 20 GB are streamed and never pass through the API layer. After upload the file is AV scanned and moves to AVAILABLE or QUARANTINED; SDEC learns the outcome from events or the status API, not from the PUT response. Used for: External User Document Upload.
Event Notification (Webhook)Boomi publishes document lifecycle events (CloudEvents 1.0, file-transfer.mft-hold.events, P01 to P05) and delivers them to an SDEC webhook endpoint as the default. SDEC may instead consume from the message broker (Boomi Event Streams). Deliveries are authenticated and signed, retried with backoff, and carry an event ID so SDEC can discard duplicates. Missed events are reconciled with one status call.
Asynchronous Managed File TransferSystem to system delivery of uploaded documents. After NRS issues a presigned URL per document, SDEC sends a transfer request and HIP File Transfer Manager moves each AVAILABLE file from Boomi MFT transient storage to NRS (and to eDMS), so SDEC never handles file content. Completion and failure are reported as events. Files are deleted from transient storage once NRS and eDMS have both acknowledged delivery (SDEC-MFT-API-03). Transfer request contract to be documented as a separate entry.
