1. Goal

Prove that Boomi MFT can carry a real scheduled file transfer across both trust boundaries, as configuration rather than as a new build, inside a two-week window.

What we prove
Leg AInternal to internal. Supplier file into the ADR landing area, replacing UTM.
Leg BInternal to external. ADR output area direct to ONS, removing the Insecure IF server hop.
The pointOne generic engine, two configuration rows, zero bespoke components. If that holds, onboarding the rest of the estate is configuration work, not development work.

5. The ADR to Data Lake migration

The ADR legacy warehouse is being migrated to the Data Lake, and both of this MVP's touchpoints sit inside that scope: the NPS file landing area on leg A and the MWS file output area on leg B. There are two ways to handle it.

Option 1, recommendedOption 2
What we doMigrate the integration now. Move the transfer off legacy IAF onto Boomi, pointing at the existing ADR database and file areas. Re-point to the Data Lake as a configuration change when the warehouse migrates.Wait for the warehouse migration to complete, then build once directly against the Data Lake endpoints.
Start date28 September. Nothing is gated on the Data Lake programme.Whenever the warehouse migration lands. Not ours to set.
Build effortTwo days now, plus a one-row endpoint change later.Two days, once.
What it provesBoth the transfer and the claim that re-pointing an interface is a configuration change rather than a rebuild.The transfer only.
What it costsOne config change at migration time, and a short period where the flow points at an endpoint with a known end date.The legacy IAF transfer keeps running on the old platform for the whole duration of the warehouse migration, and the MVP evidence arrives too late to inform the wider onboarding plan.
Main riskThe Data Lake endpoint differs enough that the re-point is not a one-row change. If so, that is a finding worth having early rather than late.The migration slips and the MVP slips with it.

Recommendation: option 1

  • It decouples the two workstreams. Neither programme waits on the other, and the two-week window survives.
  • The re-point is the same work as any endpoint change, so doing it twice costs close to nothing if the platform behaves as designed. Proving that is the point of the MVP, not a side effect of it.
  • Option 2 hands the MVP start date to a programme that does not control it. That is the substantive difference between the two.
  • Option 2 only wins if the Data Lake landing zone already exists and is reachable before day 5. If that turns out to be true, build straight to it. That is still option 1, just with a different endpoint value in the configuration row.

Conditions on option 1

ConditionOwnerNeeded by

The dependency is an argument for the MVP rather than against it. If re-pointing a migrated endpoint really is one row, the Data Lake migration makes the platform more useful, not less. If it is not one row, we need to know that now, while it costs two days rather than an estate.

6. Success criteria

RefMet when
SC-1Leg A delivers into the ADR landing area, byte identical, three consecutive runs
SC-2Leg B delivers to ONS, acknowledged, three consecutive runs
SC-3Both legs are configuration rows on one engine, zero bespoke components
SC-4The existing Maestro chain runs unchanged after Boomi delivers
SC-5The Insecure IF server hop is absent from the leg B path
SC-6Non-arrival, transfer failure and scan failure each raise an alert to a named queue, evidenced in test
SC-7One audit record per transfer: source, destination, size, checksum, timestamps, outcome
SC-8Service Operations signs the handover after a live failure and recovery walkthrough
SC-9Rollback to the incumbent path executed and timed at least once
SC-10Build effort recorded in hours, separated from time spent waiting on dependencies
SC-3 is the one that matters. Everything else can be fixed. If two similar transfers cannot both be delivered as configuration on one engine, the platform's economics do not hold and the answer is no-go.
