1. Purpose

This page describes the Boomi Managed File Transfer (MFT) platform: its two applications, Automated File Transfer (AFT) and File Sharing (FS), the runtime that keeps internal transfers inside our network, how the platform is deployed on the programme, how environments and instances are organised, the roles and access given to product teams, the naming conventions, and the gaps and decisions that shape its use. The MVP is described on the child page, Boomi MFT MVP Solution.

2. Platform at a glance

Boomi MFT is a cloud-native managed file transfer service within the Boomi Enterprise Platform. It came from Boomi's acquisition of Thru Inc., announced in May 2025, so some screens, URLs and install paths still carry the Thru name. Boomi hosts the control plane, the portal and persistent file storage. We host the MFT Node runtime inside our network wherever files must stay internal.

On the programme, Boomi MFT complements the incumbent file-transfer estate (ESDES and SDS). It is not a like-for-like replacement. New and migrated transfers are onboarded by configuration, not by building a new component for each interface.

3. Automated File Transfer (AFT)

AFT is managed file transfer as a service for system-to-system exchange. Boomi describes it with a postal model: participants drop off and pick up files, and the Flow decides where each file goes. Internal teams and systems use the same Flows to reach each other's endpoints.

3.1 Concepts

EndpointA source or target location. External endpoints: MFT connects out to a server with supplied credentials. MFT Server endpoints: MFT is the server and the partner logs in with an MFT user.Endpoints are configuration rows. Credentials are held on the endpoint (gap G-14).

3.3 Key capabilities

  • Triggering: schedules on source Flow Endpoints (four frequency options), or an API call that runs a Flow Endpoint now when an upstream event says files are ready.
  • Guaranteed delivery: files persist in MFT storage until delivered, Flow state survives retries, and failed transfers retry automatically.
  • Fan-out: a Flow can have many subscribers. If one subscriber or endpoint is disabled, the Flow still runs for the others.
  • Hybrid execution: external endpoints can be served by the Cloud or by an MFT Node (Node Direct). With Node Direct, connections start from the Node's IP addresses, so partners must allow-list those.
  • Concurrency: transfer concurrency is set per Flow Endpoint and the Node follows that setting.
  • Visibility: Activity screen and API, alert emails per Node and per Flow, and audit history.
  • Integration: the MFT Connector and APIs let Boomi Integration processes and API Management start or consume transfers.

Operational caution: when an Organization endpoint changes (for example a password or key rotation), the change must be carried to every Flow that uses it. Plan credential rotation with this in mind (G-14).

6. Instances and environments

Boomi MFT separates work at four levels: site, instance, organization, and the endpoints, users and machine users inside an organization. This section covers the first two. Organizations and roles are covered in section 7.

6.1 Site

A site is one regional deployment of Boomi MFT, addressed by a single base URL, that can host one or many instances. Everything people and systems do in MFT starts from that URL: signing in to the portal, connecting to the SFTP, FTPS and HTTPS servers that MFT hosts, opening File Sharing links and Dropbox pages, calling the MFT APIs, and MFT Nodes connecting back to the cloud.

  • Base URL: Boomi provides a default address for each site. We publish a vanity name instead (a CNAME in our DNS that points to the Boomi host), so users, partners and runbooks use an address we control.
  • Region: the site's region decides where Boomi runs the service and holds files in transit. The region for each of our sites is to be confirmed with Boomi (D-ENV-05).
  • Network: partner allow-lists and our outbound firewall rules for MFT Nodes are set per site. A rule written for the dev site does not open access to the prod site.
  • Shared, not mixed: instances on the same site share the base URL and the Boomi-managed infrastructure behind it, and nothing else.
  • Settings: which settings sit at site level and which at instance level (for example sign-in and SSO, password policy, branding, IP restrictions) is to be confirmed with Boomi (D-ENV-06).

On the programme each AFT environment is its own site with its own link: development, test, pre-production and production. A change made on the development site cannot affect the other three.

6.2 Instance

An instance is a logically isolated tenant inside a site. It cannot see or touch another instance's data, configuration or users, even when both instances sit on the same site and share its base URL.

Each instance holds its own:

  • organizations, and the endpoints, flows, users and machine users inside them
  • PGP and SSH keys and certificates
  • MFT Nodes, each set up to connect to one instance (to confirm with Boomi, D-ENV-02)
  • activity history, alerts and audit records
  • administrators, who manage only that instance

What isolation means in practice:

  • A flow can only use endpoints of organizations in the same instance. A transfer between business areas in different instances needs a location both can reach and a flow in each instance (D-ENV-01).
  • Endpoints and keys are not shared across instances. A partner that exchanges files with two business areas is set up in each instance.
  • User access is granted per instance. A person working in two business areas needs access in both.
  • Each instance needs its own MFT Nodes in every environment where it reaches internal endpoints (D-ENV-02).
  • An incident, misconfiguration or compromised account in one instance cannot reach the files or settings of another.
  • Reporting and audit are per instance, so each business area can evidence its own transfers.

6.6 Rules

  • Each instance is set up the same way on every site: the same organizations, endpoint names and flow names, with environment-specific values (hosts, paths, credentials). Promotion then changes values, not names.
  • No flow crosses an instance boundary (D-ENV-01).
  • Live data only in production. Development and test use synthetic data; pre-production data follows D-ENV-04.
  • A development Node never serves test, pre-production or production.
  • The iPaaS team administers all 12 instances. Product teams get access only to their own organization, set per environment (section 7.6).
  • Configuration moves development, then test, then pre-production, then production. There is no native CI/CD for MFT configuration (G-13), so the promotion method is a decision (D-ENV-03; D-MVP-06 covers the MVP).

7. Roles and access

Product and development teams build their own transfers under a controlled self-service model. Creating a flow is straightforward. The control point is the type and level of access each team gets, which this section sets out. It follows Approach B from the role design note: each product team is given an organization and works inside it.

7.1 Self-service context

Three transfer patterns are in scope for self-service: internal to internal (within our estate), internal to external (to trusted or untrusted external parties), and external to internal (from trusted or untrusted external parties). The MVP also tests external to external. Flows are built using one of four mechanisms, chosen by use case.

MechanismHow it worksNotes
1. Scheduled flowAn AFT flow with a schedule picks up files from a location at a set time or within a time windowDefault choice
2. API-triggered flowAn AFT flow started by an API callMany current transfers are API triggered. Confirm a schedule is not enough before using this (D-RA-07).
3. API uploadAn API call carries the file and triggers a flow that drops it at a set locationPackaged as a Boomi Integration template for developers
4. Pre-signed URLA REST endpoint returns pre-signed URLs so digital applications can upload citizen documents to a set locationSupported through an iFrame component in FS and AFT, injected into the digital front end. A pre-signed URL that can be called by API has been requested from Boomi.

For faster delivery, the API interactions in mechanisms 2 to 4 are packaged as templates in Boomi Integration that developers reuse.

7.3 Approach B: one organization per product team

The iPaaS team creates an organization for each product team, named after the product or project, in each instance and environment the team uses. Inside it the team creates endpoints (following the naming conventions in section 8), creates flows and reuses its endpoints across its flows. Teams cannot create organizations. Further organizations are created by the iPaaS team when needed. Access to another team's organization is restricted and granted only on a need basis.

  • iPaaS platform team: creates the organization, assigns the Standard_Admin and Standard_User roles, grants access to other organizations on request, and sets up sites, instances and MFT runtimes.
  • Standard_Admin (administrator): creates each organization endpoint, so connection details (protocol, host and port, credentials) are owned by the project lead.

  • Both product roles: create keys and certificates and MFT runtimes (as in the role design note, see D-RA-01 and D-RA-02), and view alerts and file activity.

8. Naming conventions (proposed)

8.1 Rules

  • Names are the same in every environment. The environment comes from the site, so promoted configuration needs no renaming. Only MFT Nodes, hosts and access groups carry an environment code.
  • Segments go in a fixed order, separated by hyphens. Codes are upper case; the purpose segment is PascalCase. Directory paths, Node names and machine users are lower case.
  • Letters, digits and hyphens only, with no spaces. Keep names under 64 characters; confirm Boomi field limits (D-NC-02).
  • No personal names in object names. Use team, system or partner names.
  • Existing objects keep their names. The convention applies to new objects.

9.1 Security baseline for every transfer

  • TLS 1.2 minimum (1.3 preferred) on every leg; no plaintext FTP.
  • Credentials held outside configuration where the platform allows, with the G-14 interim control recorded where it does not.
  • Least-privilege IAM roles and KMS keys on S3 locations used by the Node; encryption at rest throughout.
  • AV scan before any inbound file lands internally. A scanner fault fails closed and the file is not delivered.
  • An audit record per transfer: source, target, file name, size, SHA-256, start and end time, outcome and correlation ID.

1. Objective

Prove that Boomi MFT can run the four transfer directions the platform will need, across both trust boundaries, with the security, operability, delivery and audit controls a production service needs. The MVP uses synthetic or representative files in non-production. Its outputs are an evidence pack and an adoption recommendation.

2. Scope change

The earlier MVP candidate was a single live feed, ADR.040 (the quarterly Migrant Workers Scan): NPS to the ADR landing area, and ADR output to ONS. In October 2026 the MVP moved to four platform patterns with no live interface. Concept note v0.3 records this as a decision with a named owner (review finding F-01).

5. Scope

In scope

  • The four patterns in non-production, using Pega Cloud SaaS landing zones and internal S3.
  • Scheduled and API-triggered transfers.
  • AV scanning on the inbound route, with negative-path tests.
  • Alerting to the agreed channel (D-MVP-07).
  • Security controls: TLS, credential storage, least-privilege IAM, encryption at rest.
  • Configuration promotion from dev to test (D-MVP-06).
  • Audit records, evidence pack, draft runbook and support walk-through.

Out of scope

  • Live data and live interfaces, and production go-live.
  • Performance and volume testing.
  • High availability and disaster recovery failover.
  • PGP payload encryption, unless D-MVP-10 brings it in.
  • ServiceNow and Dynatrace integration; alerts go to email or Teams only.
  • File Sharing (FS).

6. Success criteria

IDCriterion
SC-1Each of the four patterns completes a scheduled and an API-triggered transfer, and the target SHA-256 matches the source.
SC-2Scheduled transfers run for at least five consecutive cycles per pattern with no manual intervention, and transfer history is visible end to end.
SC-3Non-arrival, transfer failure, AV detection and AV service failure each raise an alert to the agreed channel within the agreed time (target 15 minutes, D-MVP-07).
SC-4An infected, unscannable or oversize file is never delivered to any target.
SC-5Every transfer creates an audit record with source, destination, file name, size, SHA-256, start and end timestamps, outcome and correlation ID.
SC-6Configuration is promoted from dev to test through the agreed mechanism with no manual re-keying; rollback is demonstrated or the gap is recorded against G-13.
SC-7Security controls are evidenced: TLS 1.2 or higher on every leg, credentials held outside configuration (or the G-14 interim control recorded), least-privilege IAM on S3, encryption at rest.
SC-8The support team can restart a failed transfer, replay a transfer and investigate a quarantined file using the draft runbook, without platform team help.

7. Test approach

A pattern passes when its scheduled run and its API-triggered run both complete, the target SHA-256 equals the source, and the audit record is complete. Negative-path tests cover an EICAR test file, AV service unavailable, target unavailable, a file above the AV limit (G-15), a zero-byte file, a duplicate file and an invalid file name. The full test and evidence catalogue is published with the concept note review.
