Overview and the presigned URL question

Boomi MFT's Content API presigns download URLs only; uploading through it needs a credential with the File Upload privilege. So a native MFT presigned upload URL cannot be handed to a consumer. The design signs the URL on the S3 landing bucket that Boomi MFT uses as its source endpoint, so the file reaches MFT without its bytes passing through the gateway or the Molecule.

OptionHow it worksAssessment
A (recommended)Boomi signs an S3 SigV4 PUT URL for an object in the landing bucket. The landing bucket is the Amazon S3 source endpoint of a Boomi MFT flow, so MFT takes over as soon as the object lands.Bytes never pass through the gateway or Molecule. Reuses the existing Groovy signer and the landing bucket pattern. Needs the S3 ACL exception (D-05).
BBoomi issues its own signed token URL to a Boomi upload endpoint that streams the body into the MFT Content API with a server-side key.MFT-native storage, but up to 250 MiB per file passes through gateway and Molecule.
CBoomi requests an MFT File Sharing uploader short key and returns that link.Built for people in a browser widget, not for a system PUT.

1 Description

The consumer calls one REST operation, POST /file_uploads, to ask for permission to upload between 1 and 10 documents. For each document it sends its own externalDocumentId, the file name, the size, the MIME type and (for files up to 100 MiB) a SHA-256 checksum, plus a correlationId for the whole request.

Boomi API Management authenticates the caller and checks the request shape. A generic Boomi process applies the upload policy for the sourceSystem, issues one fileCollectionId for the request and one fileId per accepted document, and returns a presigned PUT URL per document (or one URL per 16 MiB part for files above 100 MiB). URLs live for 15 minutes and can write only the one object they were signed for.

The presigned URL points at the S3 landing bucket that Boomi MFT uses as its source endpoint. Boomi MFT itself has no presigned upload URL (its Content API presigns downloads only), so this is how the request "upload to Boomi MFT" is met without file bytes passing through the gateway or the Molecule.

Boomi MFT picks the file up, runs the anti virus flow endpoint, and delivers clean files to the clean staging bucket or blocks infected ones. Boomi reads the MFT outcome, maps the fileId back to the consumer's externalDocumentId, and publishes outcome events on Boomi Event Streams. Consumers can also poll GET /file_uploads/{fileCollectionId}.

3.1 Can many documents be uploaded, and how is the document ID mapped?

Yes. One request carries 1 to 10 documents. Each accepted document gets its own Boomi fileId and its own presigned URL (or one URL per part). The response pairs every fileId with the consumer's externalDocumentId, and fileId is the only identifier that travels through S3 and MFT. Boomi maps it back to externalDocumentId from the registry when MFT reports the outcome.

IDRule
M-01Yes, many documents can be uploaded in one request: documents[] holds 1 to 10 elements (policy maxDocumentsPerRequest). Each file still uploads separately, to its own URL.
M-02One request creates one fileCollectionId. Each accepted document gets one fileId and one presigned URL (SINGLE) or one URL per part (MULTIPART). A URL can only write the one object it was signed for.
M-03The response returns one files[] element per request element, each carrying the consumer's externalDocumentId next to the Boomi fileId. Consumers match on externalDocumentId, never on array position.
M-04externalDocumentId must be unique within the request (else 400) and must not have a live file for the same sourceSystem in another collection (else 409 EXTERNAL_ID_IN_USE).
M-05fileId is the only identifier that travels through S3 and MFT: it is the last segment of the object key and therefore the MFT file name. P03 resolves fileId back to externalDocumentId, fileCollectionId and correlationId from the registry, so no consumer data needs to survive the MFT leg.
M-06documentName is never used in keys or MFT names (PII and path safety). It is stored in the registry and carried on document_upload_requested.
M-07Acceptance is per document. If some documents fail policy checks the request still returns 201 with those elements marked REJECTED; only when none pass is 422 returned.
M-08Every per-file event carries fileCollectionId, fileId, externalDocumentId and correlationId. file_collection_completed is emitted once when all files are terminal.

5 Sample request and response

The main sample asks for three documents: a small PDF (SINGLE upload), a 150 MiB TIFF (MULTIPART, 10 parts) and a 500 MiB video that is over the 250 MiB limit and is rejected. The URLs were produced with the same SigV4 algorithm as the Boomi signer, using documentation-only credentials.

Non-functional and security design

AreaDesign
SecurityOAuth2 client credentials with scope file-transfer.upload.request; TLS 1.2+ everywhere; sourceSystem bound to client id; URLs scoped to one object, 900 s, checksum-signed for SINGLE.
IntegritySINGLE: S3 rejects bytes that do not match the signed SHA-256. MULTIPART: part ETags checked at completion; full-file checksum verified by MFT pickup where supported (validate in POC).
PerformancePOST /file_uploads p95 under 800 ms for 10 documents (signing is local; one multipart create per large file).
AvailabilitySame as the HIP API tier; P01 is stateless apart from the registry. 503 with no partial commit on dependency failure.
ObservabilitycorrelationId, fileCollectionId and fileId on every Boomi execution, registry row and event. URLs and documentName never logged.
IdempotencyIdempotency-Key per client for 24 h; at-least-once events with stable event ids.
