NRS Pull of SDEC Attachments via Boomi MFT Pre-signed Download URL

Alternative to the S3 pre-signed PUT flow · v0.1 (draft) · 13 November 2026
WhySequenceStepsAPI parametersTo confirm

1. Why this option

The original idea had NRS issue an S3 pre-signed PUT URL for SDEC to upload each attachment. A single PUT is capped at 5 GB, so 20 GB files would need a pre-signed URL for every multipart part plus create and complete calls.

Boomi MFT already exposes a pre-signed download API. SDEC delivers the file to MFT as it does today, and NRS pulls it in two calls: one authenticated call to mint a short-lived token, and one anonymous call that redeems the token and streams the bytes. NRS writes the stream into its own bucket with a normal SDK multipart upload under its IAM role, so no S3 pre-signed URLs leave AWS and the 5 GB limit does not apply.

Call 1POST /api/Files/1.0/{fileReferenceId}/presigned
Call 2GET /api/Files/1.0/presigned/{presignedUrl}/content
Token limitsmaxDownloads 1 to 10, activeDuration up to 24 h
Large filesHTTP Range supported for partial and resumable downloads

5. Points to confirm

  1. Range and maxDownloads: does each Range request count as one redemption? If not, parallel ranged GETs become an option; if so, keep one streamed GET and use Range only to resume.
  2. Token expiry mid-stream: does a download in progress continue once activeDuration passes? 20 GB at 100 Mbit/s takes about 27 minutes.
  3. How NRS learns the fileReferenceId (step 2): MFT event, SDEC message or the FileList API.
  4. Direct authenticated download: NRS already authenticates for step 5, so the authenticated "Download a file's content by file reference" GET (also Range-capable) would skip the token. The pre-signed route fits when the download runs in a separate worker that should not hold MFT credentials.
  5. Retention: when MFT deletes the file after NRS confirms receipt and checksum.
  6. Network path from NRS to MFT (DMZ or corporate VPC, public FQDN DNS).
