1. Context

SDEC documents land in Boomi MFT (AFT flow endpoint), are AV scanned and given a fileReferenceId. The submission and its metadata already reach NRS through the HIP API (SDEC-NRS-API-01). This paper assesses how the file bytes get from MFT into the NRS S3 bucket. Design case: 2 GB per document, with headroom to 20 GB.

2. Options at a glance

Blue boxes are Boomi platform, amber are NRS. Numbers on Option 3 match the call reference in section 8.

3. Option 1: NRS S3 pre-signed upload URL (push) Not recommended above 100 MB

How it works

  1. Up to 100 MB: iPaaS gets one pre-signed PUT URL from NRS (SDEC-NRS-API-02), reads the file from MFT and PUTs it.
  2. Above 100 MB: NRS opens an S3 multipart upload and issues one pre-signed URL per 100 MB part. iPaaS reads each byte range from MFT, PUTs the part, keeps the ETag, then asks NRS to complete the upload.
  3. Volume: 2 GB = 21 parts, URLs and PUTs (about 44 calls in all); 20 GB = about 205 parts.
ProsCons
  • Matches the NRS Attachment API already drafted; small change for NRS.
  • Bytes go straight into S3; the NRS service is not in the data path.
  • Outcome is known synchronously: each PUT returns an ETag and the complete call confirms the object.
  • No new inbound network path to NRS; iPaaS makes outbound HTTPS calls only.
  • Chunking above 100 MB: one URL per part, so URL count grows with file size and is hard to manage.
  • iPaaS must build a custom chunking engine (range read, buffer, PUT, ETag, retry, resume). Not an AFT configuration, so it breaks config over construction.
  • File bytes pass through Boomi Integration runtimes: memory, disk and timeout sizing per part, and Boomi cloud API limits apply.
  • URLs issued up front can expire before late parts are sent; abandoned uploads leave orphan parts in S3 unless NRS sets an abort lifecycle rule.
  • Integrity is awkward: the multipart ETag is not the file hash; per-part and whole-file checksums must be agreed.
  • Every URL is a bearer credential; hundreds per large file to mask in logs.

4. Option 2: MFT SFTP to NRS SFTP endpoint (push) Fallback

How it works

  1. NRS exposes an SFTP endpoint (for example AWS Transfer Family) that writes to its S3 bucket.
  2. NRS is set up as an organization endpoint in Boomi MFT; an AFT flow delivers each clean document to it.
  3. Files are named, or carry a manifest, with nrsSubmissionId, nrsAttachmentId and SHA-256 for correlation.
  4. NRS detects arrival, binds the file to the submission and confirms to iPaaS by API or event.
ProsCons
  • Native AFT capability: a configuration row, not code.
  • No chunking or URL handling; one SFTP session streams a file of any size, several files per session if needed.
  • MFT gives retry, scheduling, delivery tracking and audit out of the box.
  • Bytes never pass through Boomi Integration.
  • NRS must build and operate a new inbound SFTP service: endpoint cost, SSH keys (rotation across two teams), user and directory mapping, hardening.
  • Inbound SFTP to NRS needs allow-listing of MFT egress IPs and firewall changes. It cannot sit behind the HTTP API gateway, so it bypasses API security controls.
  • File and submission are decoupled: correlation relies on naming or a manifest, a weaker binding for non-repudiation.
  • SFTP success means bytes written, not NRS accepted; a separate acceptance callback and reconciliation are needed.
  • Partial-file risk: NRS must not process until the upload is complete (temp name and rename, or completion event).

5. Option 3: NRS pull via Boomi MFT Content API pre-signed download Recommended

How it works

  1. iPaaS sends NRS one API message per document: fileReferenceId, endpointPath, size, SHA-256 (call 1).
  2. NRS calls the MFT Content API to mint a short-lived, use-limited download token for that file (call 2).
  3. NRS redeems the token with a GET that streams the content (call 3) straight into an S3 multipart upload under its own IAM role (step 4).
  4. NRS verifies the SHA-256 and calls back ACCEPTED or REJECTED (step 5); iPaaS then releases the file in MFT. 4 to 5 calls per document, whatever the size.
ProsCons
  • Size independent: no chunk URLs for the sender. Boomi states the Content API streams large files (10 GB example).
  • Resumable: HTTP Range (206) lets NRS restart from the last byte received.
  • No file bytes through Boomi Integration and no custom transfer code: iPaaS sends a small JSON message to a published Boomi API.
  • Asynchronous by design: NRS controls pace and concurrency; no long-held connections from iPaaS.
  • Strong binding for non-repudiation: fileReferenceId and SHA-256 travel in the API call; MFT records the download.
  • Token is limited in time (max 24 h) and uses (1 to 10). S3 stays private to NRS; NRS needs outbound HTTPS only.
  • Largest change sits with NRS: a new downloader worker, and the attachment contract moves from issuing URLs to accepting a reference.
  • NRS needs an MFT credential (OAuth2 client or ApiKey with File Download) scoped to the SDEC flow endpoint, with rotation agreed.
  • Network: NRS needs egress to the Boomi MFT regional host (https://{region}-api.mft.boomi.com).
  • Retention coupling: the file must stay in MFT until NRS confirms; purge rules and late pulls need design.
  • To confirm with Boomi: whether each Range request counts against maxDownloads, whether a stream survives token expiry, rate limits and throughput (none published).
  • No download checksum header, so integrity relies on the SHA-256 sent in call 1. The token is a bearer secret in the URL path; mask it in logs.

Variant 3b: iPaaS mints the token and sends it in call 1, so NRS holds no MFT credential. If NRS does hold one, the authenticated GET /api/Files/1.0/{fileReferenceId}/content (Range capable) removes the token step.

7. Recommendation and decisions

Recommendation. Adopt Option 3 as the target pattern for all document sizes. It removes chunking from the sender, keeps file bytes out of Boomi Integration and binds each file to its submission through the API call. Keep Option 2 as the fallback if NRS cannot build a pull client. Do not use Option 1 above 100 MB.

8. Option 3 API call reference

Base host https://{region}-api.mft.boomi.com (regions us, eu, uk, au). Calls 2 and 3 are the Boomi MFT Content API Download operations; call 1 extends the drafted NRS Attachment API.

#DirectionOperationDetail
1iPaaS to NRSPOST /nrs/submissions/{nrsSubmissionId}/attachmentsJSON: fileReferenceId, endpointPath, fileName, fileSizeBytes, checksumSha256. NRS returns 202 Accepted.
2NRS to MFTPOST /api/Files/1.0/{fileReferenceId}/presignedAuth: OAuth2 client credentials or ApiKey, privilege File Download. Body: endpointPath, maxDownloads (1 to 10), activeDuration (1 to 86400 s). Returns 200 {"presignedUrl": "<token>"}.
3NRS to MFTGET /api/Files/1.0/presigned/{presignedUrl}/contentNo auth header; the token authorises. 200 application/octet-stream stream, 206 with Range header for resume. 404 token expired or exhausted.
4NRS to S3S3 multipart upload (AWS SDK, NRS IAM role)Internal to NRS. No S3 pre-signed URLs leave NRS.
5NRS to iPaaSCallback or event: ACCEPTED / REJECTEDCarries nrsAttachmentId and verified SHA-256. iPaaS then releases the file in MFT.
