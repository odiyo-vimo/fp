4. Authentication: OAuth 2.0 Client Credentials

All SDEC integration patterns use OAuth 2.0 client credentials. SDEC exchanges its client ID and secret with iPaaS for a short-lived bearer token, then presents that token on every API call. iPaaS both issues and validates the token. The integration supports app-to-app authentication only.

Key points

TopicGuidance
Grant typeClient credentials (RFC 6749, section 4.4). Machine to machine, no user involved, no refresh token. When the token expires, SDEC requests a new one.
Token issueriPaaS issues and validates the tokens through its own token endpoint. There is no separate authorisation server in the flow.
Who callsOnly the SDEC backend holds the client secret and calls the token endpoint and the APIs. The browser only ever receives a presigned URL.
Client registrationOne client per environment (dev, test, pre-prod, prod). Each client ID maps to one sourceSystem value and a fixed set of scopes.
Token requestPOST /oauth2/token with form-encoded grant_type=client_credentials and the scopes needed. The client authenticates with HTTP Basic (client ID:client secret) over TLS.
Token responseaccess_token (signed JWT), token_type Bearer, expires_in (proposed 3600 seconds, D-13) and the granted scope.
Using the tokenSend Authorization: Bearer <access_token> on every API call. Never put the token in a query string, URL or log line.
CachingReuse the token until shortly before expiry (for example renew when less than 60 seconds remain). Do not request a token per API call; the token endpoint is rate limited.
Validation in iPaaSSignature, issuer, audience, expiry and not-before (small clock-skew allowance), scope against the operation, and client ID against sourceSystem.
Errors401 invalid_token: discard the cached token, request a new one once and re-try the call. 401 invalid_client or 403 insufficient_scope: configuration fault; log, alert and do not re-try.
Secret rotationTwo secrets are valid during a rotation window so SDEC can switch without downtime. Rotation period agreed with security (D-13).
Hardening optionprivate_key_jwt (RFC 7523) or mutual TLS client authentication (RFC 8705) removes the shared secret. Recommended for decision before go-live (D-15).

Sequence diagram

Success: token request and caching happen once per token lifetime; the API request repeats for every call while the token is valid. NRS is only called for the NRS APIs, and iPaaS uses its own NRS credentials on that leg (S-14). Token Expired: one re-try with a new token. Invalid Credentials: no re-try.

5. Integration Patterns (section 5.2)

Pattern

PatternDescription
Synchronous APIRequest and response over HTTPS (REST, JSON) to iPaaS; SDEC receives the result in the same call. Used for: generate presigned URL (SDEC-MFT-API-01), get document status (SDEC-MFT-API-02), delete file (SDEC-MFT-API-03), NRS submission (SDEC-NRS-API-01) and NRS attachment URL (SDEC-NRS-API-02). Controls: OAuth 2.0 bearer token, Idempotency-Key on create and delete, X-Correlation-ID, agreed timeouts, Problem error structure. No file content passes through this pattern.
Asynchronous File UploadSDEC obtains a time-bound presigned URL through the synchronous API, then the browser uploads the file directly to iPaaS transient storage with HTTP PUT. Files up to 20 GB are streamed and never pass through the API layer. After upload the file is AV scanned and moves to AVAILABLE or QUARANTINED; SDEC learns the outcome from events or the status API, not from the PUT response. Used for: External User Document Upload.
Event Notification (Webhook)iPaaS publishes document and transfer events (CloudEvents 1.0) on its message broker and calls back an SDEC webhook with the document ID as the default. SDEC may instead consume from the broker directly. Callbacks are authenticated, re-tried with backoff and carry an event ID so SDEC can discard duplicates. Missed events are reconciled with one status call.
Asynchronous File TransferSDEC sends Transfer Document (document ID, NRS presigned URL) and iPaaS acknowledges straight away. iPaaS publishes a transfer request event on its broker, consumes it, locates the document in transient storage and uploads it to the NRS presigned URL. On success it publishes a success event and calls back SDEC; on failure it re-tries, then publishes a failed event and calls back SDEC. SDEC never handles file content. Files are deleted once NRS and eDMS have both acknowledged delivery (SDEC-MFT-API-03).

5.2.x Sync Create Thread (Contact Details) from SDEC MDTP to SDEC HCP

Ref #SDEC-HCP-API-01
Integration Flow TitleSync Create Thread (Contact Details) from SDEC MDTP to SDEC HCP through iPaaS
Diagram
Additional Information
Purpose & OutcomeIntegration flow responsible for creating a thread in SDEC HCP when the user saves their contact details in SDEC MDTP. The process is completed synchronously: SDEC MDTP sends the create thread request through iPaaS to the Thread Service API in SDEC HCP Thread Manager, which generates the thread reference (technical and business facing), sets the thread state to Pending Thread Created and returns the reference in the same call. SDEC MDTP then displays the Send / Request File page.
Input/Submitted DataHeaders: Authorization (Bearer token, OAuth 2.0 client credentials, scope thread.create (proposed)), Idempotency-Key (UUID), X-Correlation-ID (UUID).
Body (JSON): sourceSystem (SDEC-MDTP) and contactDetails: firstName, lastName, emailAddress, mobileNumber, nino.
Output/Response DataThread created response (201 Created, JSON) with metadata: threadId (technical reference), businessReference (user-facing reference), status PENDING_THREAD_CREATED, createdAt and correlationId. Field names to be aligned to the HCP Thread Service API (D-22).
CRUDPOST
TriggerUser (SDEC MDTP Front End) selects "Continue" on the Contact Details page; SDEC MDTP persists the contact details and triggers the Create Thread request to SDEC HCP (Create Thread V4, steps 6 to 12).
Exception/Error Handling400: request schema invalid (missing field, invalid email, mobile or NINO format); errors[] returned and shown against the fields. 401/403: token missing, invalid or lacking scope. 409: repeat call with the same Idempotency-Key returns the original thread reference. 422: HCP business validation failure. 429: rate limit exceeded; re-try after Retry-After. 502/503: HCP error or unavailable. 504: no response within the timeout (D-24); outcome unknown, so SDEC MDTP re-tries with the same Idempotency-Key. iPaaS re-tries transient HCP failures only if HCP supports idempotency (D-23). All errors use the Problem structure with correlationId. Contact details (including NINO) are masked in iPaaS logs; the payload is not logged.
Delivery Group ImpactsSDEC MDTP: call the iPaaS API instead of HCP directly, manage the OAuth token, generate and persist the Idempotency-Key, store the thread reference, and handle errors on the Contact Details page.
iPaaS: new synchronous API, request schema validation, OAuth scope, routing and credentials to HCP, timeout and re-try policy, masking of personal data in logs.
SDEC HCP: expose the Thread Service API to iPaaS, generate technical and business references, support Idempotency-Key, and clean up orphaned pending threads.
Additional NotesSynchronous request and response; no file content. Contact fields from Create Thread V4: First Name, Last Name, Email Address, Mobile Number, NINO. Pending threads abandoned by the user are removed by the HCP retention policy. Save thread details (step 21, PUT Thread Service API) is a separate entry.
